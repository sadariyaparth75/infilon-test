Authentication

API key: from configuration, never from code

  • Three sources, first one wins: environment variable, .NET user secrets, appsettings.json
  • appsettings.json is in .gitignore; the repo has only appsettings.example.json as a template
  • Fails fast: no key means a clear instruction and exit code 1, instead of silently empty lists
  • Rejected key (401 / 403) gets its own message
  • Found while testing: the API answers an invalid key with 403, not the 401 mentioned in the PDF
// Program.cs: later sources override earlier ones
new ConfigurationBuilder()
    .SetBasePath(AppContext.BaseDirectory)
    .AddJsonFile("appsettings.json", optional: true)
    .AddUserSecrets<Program>(optional: true)
    .Build();

// ApiSettings: the environment variable wins
var apiKey = Environment.GetEnvironmentVariable(
    "SOLAR_SYSTEM_API_KEY");
if (string.IsNullOrWhiteSpace(apiKey))
    apiKey = configuration["SOLAR_SYSTEM_API_KEY"];
// HttpClientService constructor
Client.DefaultRequestHeaders.Authorization =
    new AuthenticationHeaderValue(
        "Bearer", apiSettings.ApiKey);
  • The environment variable wins, so a key can be overridden per run (for example in CI) without touching stored secrets.
  • appsettings.json is the simplest option and one the PDF names explicitly: "an appsettings file excluded via .gitignore". User secrets and the environment variable stay available.
  • You can run it with your own key: copy the example file and paste your key in. The README shows how.

Domain model changes

Temperature as a first-class, nullable value

  • Moon.AverageTemperature: float? in Kelvin
  • Planet.AverageMoonTemperature replaces the AverageMoonGravity stub
  • Planet.MoonsWithKnownTemperatureCount: how many moons the average is based on
  • Planet.AverageTemperature: the planet's own value, as a reference

Why nullable?

The API sends avgTemp = 0 when it has no data. 0 K is absolute zero, which is physically impossible, so it means "unknown". If 0 were averaged in, the result would be dragged down and misleading.

// TemperatureUtility
public static float? FromApiValue(float kelvin)
    => kelvin > 0 ? kelvin : (float?)null;

// Planet
public float? AverageMoonTemperature
{
    get
    {
        var knownTemperatures = Moons?
            .Where(m => m.HasKnownTemperature)
            .Select(m => m.AverageTemperature.Value)
            .ToList();

        if (knownTemperatures == null
            || knownTemperatures.Count == 0)
            return null;   // "unknown", not 0

        return knownTemperatures.Average();
    }
}
  • The PDF pointed at the planet's average method as a starting point. I kept the logic there, because averaging is a domain rule, not a display concern.
  • Nullable is the key decision: "no data" and "zero" must be different things.
  • The moon count is there so the reader can judge how much an average is worth.

API interface changes

From hundreds of requests to two

Before
~915

1 planet list + 1 request per moon, run again for each of 2 output lists, + 1 moon list

After
2

1 planet list + 1 bulk moon list, loaded once and reused for every output

  • Bulk moon request with avgTemp and aroundPlanet; moons are matched to planets in memory by id
  • bodyType,eq,Moon instead of aroundPlanet,gt,null: 479 moons instead of 336
  • Nested fields listed explicitly in data=, otherwise the API returns empty objects
  • semimajorAxis spelled the way the API spells it
  • One GetFromJson<T> helper: status checks, clear errors
  • ~915 for the original code (once it builds and has a key): 1 planet call plus 456 moon calls, done for each of the 2 lists that read planets, plus 1 moon list call.
  • Fewer calls means faster runs, less load on a free public API, and fewer chances to fail partway.
  • I verified each query change against live responses before changing the code.

An honest result

The API has no moon temperatures

All 479 moons return avgTemp = 0. I checked the list endpoint and individual moons (Lune, Titan, Europe, Triton, Io).

So every moon average is "n/a". The output makes that visible instead of hiding it:

  • "Moons With Temperature Data" column shows 0
  • A note under the table explains why
  • The planet's own temperature is shown separately, not substituted
  • When the dataset gains moon temperatures, the averages appear with no code change
Decision

Why not estimate a value?

Filling the gap with the planet's temperature would print numbers that look real but aren't. In a data tool, a visible "unknown" is more useful than a confident wrong value.

  • This is a data limitation, not a code limitation. The calculation is in place and handles the case correctly.
  • If asked: yes, I could approximate, but I'd make it opt-in and clearly labelled as an estimate.

Robustness

Error handling and user feedback

Step 1

Load data

"Loading data…" then a summary line with counts. On failure the run stops, because there is nothing to write.

Step 2

Write to screen

A step message before each list. A failure here is reported, but does not block step 3.

Step 3

Write to files

Three CSV files in FileOutput/. Each folder and file created is announced on screen.

  • Failed requests throw a clear error instead of returning an empty list that looks like "no planets found"
  • log4net logs warnings and errors with stack traces; any failure sets exit code 1
  • Invalid API entries (null, no id) are skipped safely; unmatched moons are logged
  • The original code returned an empty list on errors, so a missing or wrong key looked exactly like "the API has no planets". Now it says what went wrong.
  • The exit code matters if this ever runs in a script or a scheduled job.

Reflection

Trade-offs and next steps

Deliberate trade-offs

  • Synchronous calls: with only 2 requests, async through every layer added little. It's the first thing to change if calls grow.
  • In-memory cache per run, not on disk
  • Existing structure kept (log4net, Newtonsoft, console writer), so changes stay reviewable

With more time

  • Unit tests for the averaging and the moon matching
  • Async/await end to end, with retry on network errors (Polly)
  • Sort planets by distance from the Sun, and show English names (englishName)
  • Shared table model for screen and CSV, to remove duplication
  • The PDF says the aim isn't complex optimised code but how I solve problems, so I focused on correctness, honesty about the data, and clear reasoning.
  • Be ready to defend sync vs async: a simple choice for a 2-request console app, with a clear path to change it.
